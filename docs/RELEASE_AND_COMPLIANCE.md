# Release and Play Compliance

Facts marked (verified Oct 2026) were checked against current Google sources when this pack was written. Everything else must be re-checked in Play Console and Android documentation before release.

## 1. Platform requirements
- (verified Oct 2026) New apps and updates must target Android 16 (API 36) or higher on Google Play. Existing apps must target at least API 35 to remain available to new users on newer devices.
- (verified Oct 2026) Android 17 (API 37) is released, and Play had set no target deadline for it at the time of writing. Test on it now. Target it only after an explicit migration milestone.
- Expect the target requirement to rise yearly. Schedule a platform-update milestone every spring, when new Android betas appear, and finish before the summer deadline.
- Google Play requires 16 KB page-size compatibility for native code. Verify all native libraries, including transitive ones.

## 2. Accessibility API compliance
- (verified Oct 2026) Apps not eligible for the accessibility-tool designation must not use that flag, must show a prominent disclosure and get consent, and must prefer narrower APIs where possible. The disclosure must be a separate in-app screen. The service description text does not count.
- (verified Oct 2026) The Play Console declaration requires explaining why the API is needed and a video showing the disclosure flow and the core feature using it.
- The core functionality must be documented and promoted in the store description.
- Script for the declaration video: open app, show onboarding, show the disclosure screen, tap agree, show system settings enabling the service, return to app, open a blocked feed and show the exit behaviour, then show how to turn it off.

## 3. Other declarations and forms
- Foreground service type declaration with a justification of why the chosen type fits.
- Data Safety form, privacy policy URL, content rating questionnaire, target audience and content, ads declaration, app access instructions for reviewers (provide a test account if sign-in is required).
- Account deletion URL if accounts can be created in the app.
- Permissions declarations for any restricted permission. Avoid restricted permissions unless essential.
- Check closed-testing requirements for your developer account type in Play Console (some personal accounts have had minimum tester and duration rules). Plan the timeline accordingly.

## 4. Store listing
- Honest title, short description and full description. State what the app does, which permissions it needs and why.
- Do not claim to treat addiction or mental-health conditions.
- Original icon, screenshots, feature graphic and copy. No assets from other apps.
- Screenshots show real UI, including the permission explanation screens.
- Localise at least English, Hindi and Marathi if those are launch languages.

## 5. Versioning and branching
- Semantic version names and monotonically increasing version codes, generated by CI.
- Trunk-based development with short-lived feature branches and pull requests, even as a solo developer.
- Conventional commit messages. Tag every release.
- Play App Signing enabled. The upload key is stored securely and backed up.

## 6. Release pipeline
1. Pull request checks: build, lint, static analysis, unit and ViewModel tests.
2. Merge to main: instrumented tests on emulators, rules and Functions tests, build release bundle.
3. Internal testing track: owner and a few devices.
4. Closed testing: broader cohort across the device matrix.
5. Review the Play pre-launch report.
6. Production with a staged rollout: start small (for example 5 to 10 percent), watch metrics, then expand.
7. Rollback plan: halt the rollout, flip kill switches in Remote Config, ship a fix.

## 7. Release checklist
- Target API and compile SDK correct, 16 KB check passed.
- Release build tested end to end (obfuscation can break things).
- Permission flows and disclosures re-tested on a clean install on three OEM devices.
- Safe-list tests passing and manually verified.
- Remote Config defaults and kill switches verified.
- Store listing, privacy policy and Data Safety updated and consistent with the build.
- Accessibility declaration and video current.
- Crash and analytics dashboards ready, alerts configured.
- Support email and in-app feedback working.
- Release notes written.

## 8. Post-launch monitoring
Track crash and ANR rates by OS version and brand, onboarding funnel and permission drop-off, blocker-still-alive rate after 7 days, battery complaints, Firebase cost, and review sentiment. Check Android vitals thresholds in Play Console, since exceeding them can reduce visibility.

## 9. Maintenance cadence
- Weekly: crash triage and review replies.
- Monthly: dependency updates, Remote Config identifier checks against current YouTube and Instagram releases.
- Quarterly: privacy and permission review, device-matrix regression.
- Yearly: target API migration, policy re-read, accessibility and design review.
